I found a case where narrowing `references_model()` for `RemoveConstraint` reorders operations unsafely.

A foreign key with `to_field` can depend on a `UniqueConstraint` on the target model. Operations that remove such a foreign key, like `AlterField()` to a non-relational field, don't reference the target model, because operations only describe a field's new state. With this PR, these operations:

```python
[
    migrations.AlterField("Horse", "pony", models.IntegerField()),
    migrations.RemoveConstraint("Pony", "pony_code_uniq"),
    migrations.RemoveField("Horse", "pony"),
]
```

are optimized to:

```python
[
    migrations.RemoveConstraint("Pony", "pony_code_uniq"),
    migrations.RemoveField("Horse", "pony"),
]
```

where `Horse.pony` was `ForeignKey(Pony, models.CASCADE, to_field="code")`. That drops the unique constraint while the foreign key still exists, which fails on PostgreSQL:

```
django.db.utils.InternalError: cannot drop constraint pony_code_uniq on table app_pony because other objects depend on it
```

`RemoveConstraint` only has a name, so it can't tell whether it's removing a unique constraint. The fix is to keep it referencing all models:

```python
class RemoveConstraint(IndexOperation):
    ...

    def references_model(self, name, app_label):
        # The removed constraint may be a unique constraint that foreign keys
        # on other models depend on. Operations removing such foreign keys
        # don't reference this model, e.g. AlterField() to a non-relational
        # field, so they must not be moved after this operation.
        return True
```

With that, the example is optimized safely to `RemoveField` then `RemoveConstraint`. The other operations are fine: `AddConstraint` and `AlterConstraint` can't break foreign keys on other models, and a plain `Index` can't back a `to_field`.
